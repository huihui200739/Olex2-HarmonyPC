# 诊断包构建来源追溯

日期：2026-11-09（Asia/Shanghai）

本轮补齐的是完整路线 P6 的一部分：让诊断应用的源码、构建输入、包内代码和实际安装验证能够逐层对照。没有增加业务功能，也没有把完整适配目标缩小为诊断应用。应用仍为 0.10.0 未签名 debug；完整原界面、完整渲染器、Python/插件和发行验收仍未完成。

## 实现

- `scripts/build-app.sh` 先检查固定上游、六份补丁与许可证，再在独占英文临时目录复制源码。没有重命名工作区、修改 SDK 或复用原生构建输出。
- `scripts/build_provenance.py capture` 在依赖解析后记录这份实际快照。已有源码必须与工作区逐字节一致；只允许新出现的本地依赖锁文件，其他意外生成源码、符号链接或复制后改动会失败。
- 包内 `resources/rawfile/OLEX2-BUILD-INPUTS.json` 保留源码路径、长度、SHA-256、来源类别、固定提交、补丁与构建脚本摘要、11 项选定工具标识及 Native SDK 元数据。不保存用户签名资料或本机私有设置。
- 开启实际原生编译数据库，构建后读取 `compile_commands.json` 和 Ninja 的有效依赖记录。源文件必须来自本次快照，项目头文件必须与捕获内容一致，SDK 输入分别标识；缺失、陈旧或不完整的对象依赖记录会失败。
- `finalize` 再核对源码没有在构建期间变化、包内清单与捕获一致、包身份一致，并要求包内原生库与这次全新构建的剥离输出逐字节匹配。全部通过才发布 HAP 和旁侧来源记录。
- `check-app-package.py` 对当前源码、HAP 和旁侧记录重新验证；摘要一致性检查也直接验证来源链，并将实际编译的上游文件集合与原有构建纳入指标比对。
- 应用验证先把 HAP、来源记录和包内输入清单保存在本轮报告目录，再核对并安装这份保留副本。后续构建覆盖 `out/app` 时，不会丢失这轮实际安装的包。

## 产物和验证方式

- 当前包：`out/app/entry-default-unsigned.hap`。
- 构建记录：`out/app/entry-default-unsigned.provenance.json`。
- 原生包检查：`reports/app/package-verification.json` 的 `build_provenance`。
- 实际安装报告：`reports/app/last-run.json`，其 `build_provenance` 指向本轮保留的 HAP、来源记录和输入清单。

```sh
./scripts/build-app.sh
python3 scripts/build_provenance.py verify \
  --hap out/app/entry-default-unsigned.hap \
  --provenance out/app/entry-default-unsigned.provenance.json \
  --workspace .
python3 scripts/run-app-smoke.py --target 127.0.0.1:5555
python3 scripts/check-app-package.py
# 仅在当前0.10.0已有保留构建/测试日志时同步摘要，再独立检查
python3 scripts/sync-verified-reports.py
python3 scripts/check-adaptation-status.py
python3 -m unittest discover -s scripts/tests -v
```

`verify` 的 `--workspace` 是当前源码一致性检查。省略它可以核对保留的历史包与来源记录，但输出会明确 `workspace_matches=false`，不能据此宣称历史包对应现在的源码。
